## 延迟/定时消息
延迟消息是什么->应用场景->延迟级别->实现原理->定时消息->与其他方案对比->面试高频题
### 延迟消息是什么
延迟消息：发送后不立即投递，而是延迟指定时间后才被消费者消费。
```
// 普通消息：发 → 立即可消费
// 延迟消息：发 → 等 N 秒/分钟 → 才可消费
```
应用场景
```
// ① 订单超时取消：下单 30 分钟后未支付 → 取消
// ② 延迟通知：支付成功后 10 分钟再发评价邀请
// ③ 定时任务：每天固定时间执行（用延迟消息替代）
// ④ 重试延迟：失败后延迟重试
// ⑤ 秒杀关闭：活动结束延迟关闭入口
```
### 延迟级别
RocketMQ只支持固定18个级别
```
// 延迟级别（DelayTimeLevel）：
// 1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h

// 级别 1 → 1s
// 级别 2 → 5s
// 级别 3 → 10s
// 级别 4 → 30s
// 级别 5 → 1m
// ...
// 级别 18 → 2h

// 注意：不能自定义任意延迟时间！
// 只能选 18 个固定级别中的一个
```
为什么固定级别
```
// ① 实现简单（18 个延迟队列预建）
// ② 性能好（不用扫全部消息）
// ③ 限制延迟时间范围（1s ~ 2h）

// 如果要任意时间 → 用定时消息（4.0+）或时间轮
```
### 使用方式
```
// 设置延迟级别
Message message = new Message("order-topic", "created", body);

// 延迟 30 秒（级别 4 = 30s）
message.setDelayTimeLevel(4);

// 或 5.0+ 直接传时间：
// message.setDelayTime(30, TimeUnit.SECONDS);

producer.send(message);
// 消费者 30 秒后才能收到
```
订单超时取消示例
```
// 下单 → 发延迟消息（30 分钟后）
// 消费者：收到消息 → 查订单 → 未支付则取消

public void createOrder(Order order) {
    // ① 落库
    orderService.create(order);

    // ② 发延迟消息（30 分钟 = 级别 16？）
    // 30m = 级别 15（30m）
    Message msg = new Message("order-timeout-topic", "check",
        order.getId().toString(), body);
    msg.setDelayTimeLevel(15);  // 30 分钟后检查
    producer.send(msg);
}

// 消费者
public void onTimeoutCheck(MessageExt msg) {
    Long orderId = ...;
    Order order = orderService.getById(orderId);
    if (order != null && "PENDING".equals(order.getStatus())) {
        orderService.cancel(orderId, "超时未支付");  // 取消
    }
}
```
### 实现原理
延迟消除的存储
```
// ① 发送时：消息存入"延迟队列"（按延迟级别分区）
// ② 到了延迟时间：把消息从延迟队列 → 转到普通队列
// ③ 消费者：从普通队列消费

// 结构：
// 延迟队列（ScheduleLog）→ 到期转移 → 目标 Topic
```
时间轮/定时扫描
```
// ① RocketMQ 用"延迟消息存储 + 定时扫描"
// ② 一个线程定时扫描到期的延迟消息
// ③ 到期 → 投递到真实 Topic
// ④ 精度：秒级

// 对比 Kafka 的精确定时：
// RocketMQ 延迟消息是"分级"的（1s~2h 18 级）
// 不是任意精度
```
### 定时消息
| 对比      | 延迟消息       | 定时消息       |
| ------- | ---------- | ---------- |
| **设定**  | 延迟级别（相对时间） | 绝对时间（时间戳）  |
| **精度**  | 秒级（分级）     | 毫秒级        |
| **灵活性** | 18 个级别     | 任意时间       |
| **版本**  | 老版本        | 5.0+ / 增强版 |
```
// 5.0+ 定时消息：
Message message = new Message("order-topic", "created", body);
// 指定未来时间戳（绝对时间）
message.setDeliverTimeMs(System.currentTimeMillis() + 30 * 60 * 1000);
producer.send(message);
```
### 与其他方案对比
| 方案                  | 实现        | 精度  | 复杂度 |
| ------------------- | --------- | --- | --- |
| **RocketMQ 延迟消息**   | 18 级别     | 秒级  | 低 ✅ |
| **RabbitMQ 延迟队列**   | TTL + DLX | 秒级  | 中   |
| **Redis ZSet 延迟队列** | 扫描过期 key  | 秒级  | 中   |
| **时间轮（Netty）**      | 内存时间轮     | 毫秒级 | 高   |
| **Kafka 定时**        | 无原生，需配合   | —   | —   |
选型
```
// ① 简单延迟（秒~小时）→ RocketMQ 延迟消息 ✅
// ② 精确到毫秒 → 时间轮（高性能场景）
// ③ RabbitMQ 生态 → TTL+DLX
// ④ 不引入 MQ → Redis ZSet 简单实现
```

### 面试高频题
#### 延迟消息是什么
```
// 发后延迟指定时间才可消费
// 订单超时、延迟通知
```
#### 延迟级别有哪些
```
// 18 个固定级别：1s ~ 2h
// 不能任意自定义
```
怎么实现订单超时取消
```
// 延迟消息：下单发 30m 延迟消息
// 消费者检查未支付则取消
```
延迟消息和定时消息的区别
```
// 延迟：相对时间（18 级）
// 定时：绝对时间（毫秒级，5.0+）
```
不用MQ怎么做延迟
```
// Redis ZSet（score=到期时间戳）+ 定时扫描
// 或定时任务扫库
```
#### 为什么不用定时任务
```
// 定时任务每分钟扫全表：海量订单全扫 → 效率低
// 延迟消息：只处理到期的 → 精准高效
```
