## 消息模型
两种消费模式->集群模式->广播模式->消费进度管理->顺序消息->面试高频题
### 两种消费模式
| 模式                     | 说明            | 场景        |
| ---------------------- | ------------- | --------- |
| **集群模式（Clustering）**   | 一条消息只被一个消费者处理 | ✅ 默认，任务分配 |
| **广播模式（Broadcasting）** | 一条消息被所有消费者处理  | 每台都处理     |
```
// 设置模式：
consumer.setMessageModel(MessageModel.CLUSTERING);    // 集群（默认）
consumer.setMessageModel(MessageModel.BROADCASTING);  // 广播
```
### 集群模式
```
// 同一个消费组（Group）内的多个消费者
// 一条消息只被组内一个消费者消费（负载均衡）
// 类似 Kafka 的 Consumer Group

// 例：订单服务 3 个实例（同一个 Group）
// 消息1 → 实例1
// 消息2 → 实例2
// 消息3 → 实例3
// （分摊处理，一条只处理一次）
```
负载均衡
```
// 消息按 Queue 分配给消费者：
// Topic 有 4 个 Queue，组内有 2 个消费者：
// 消费者1 → Queue 0, 1
// 消费者2 → Queue 2, 3

// 分配算法：平均分配（Queue 为最小单位）

// 注意：
// 一个 Queue 同一时刻只能被一个消费者消费
// 消费者数 > Queue 数 → 部分消费者空闲
```
容错
```
// 消费者挂了 → 重新分配 Queue（rebalance）
// 消费者增加 → 重新分配（均衡）
// 消息不重复？→ 不一定！处理中挂了可能重复
// （消费进度未提交 → 重新消费）
```
### 广播模式
```
// 同一个消费组内的所有消费者
// 每条消息都被每个消费者消费

// 例：订单通知组 3 个实例
// 消息1 → 实例1 ✅ 实例2 ✅ 实例3 ✅（都处理）
```
适用场景
```
// ① 每台机器都需要完整数据（本地缓存同步）
// ② 通知所有实例（刷新本地配置）
// ③ 每台独立处理完整数据（如每个节点都要全量统计）
```
注意
```
// ① 广播模式本地存储消费进度（不同步）
// ② 消费者数量变化不影响（各自消费）
// ③ 性能开销大（每条都要发给所有）
// ④ 不常用（除非确实需要）
```
### 集群 vs 广播
| 对比       | 集群模式      | 广播模式  |
| -------- | --------- | ----- |
| **消息消费** | 一条一人      | 一条所有人 |
| **消费进度** | Broker 存储 | 本地存储  |
| **负载均衡** | ✅         | ❌     |
| **容错**   | 挂了重分配     | 各自为政  |
| **适用**   | ✅ 任务处理    | 全量同步  |
| **默认**   | ✅         | 需显式设置 |
```
// 集群 = 分工（一条消息只处理一次）
// 广播 = 复制（每条消息都处理）

// 面试一句话：
// "集群模式一条消息只被组内一个消费者处理（任务分工），
//  广播模式每条消息被所有消费者处理（全量同步）。
//  默认集群，广播用于每个实例都需要完整数据的场景。"
```
### 消费进度管理 offset
消费进度存哪
```
// 集群模式：Broker 存储（每个 Consumer Group 记录 offset）
// 广播模式：消费者本地存储

// 消费进度作用：
// ① 断点续传（重启后从上次位置继续）
// ② 防止重复消费（已消费的跳过）
// ③ 回溯消费（手动重置 offset）
```
消费失败与重试
```
// ① 消费失败 → 消息进入重试队列
// ② 重试 16 次（默认）仍失败 → 进入死信队列
// ③ 死信队列需要人工处理

// 重试间隔：
// 10s、30s、1m、2m ...（递增）
```
消费模式
```
// ① 并发消费（默认）：多线程消费
// ② 顺序消费：单线程按序消费（顺序消息用）
```
### 顺序消息
为什么要顺序
```
// 订单状态流转：创建 → 支付 → 发货
// 如果乱序：支付先到，创建后到 → 逻辑错乱！

// 需要保证：同一个订单的消息按顺序处理
```

|类型|说明|实现|
|---|---|---|
|**全局顺序**|所有消息严格有序|1 个 Topic 1 个 Queue|
|**分区顺序**|同一 key 的消息有序|按 key 选同一 Queue|
分区顺序实现
```
// ① 生产端：按订单 ID 选 Queue（hash）
Message message = new Message("order-topic", tag, body);
// 指定消息发送到哪个 Queue（同一订单 → 同一 Queue）
SendResult result = producer.send(message, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        Long orderId = (Long) arg;
        int index = (int) (orderId % mqs.size());  // 按订单取模
        return mqs.get(index);
    }
}, orderId);
// 同一订单 → 同一 Queue → 顺序存储

// ② 消费端：顺序消费（单线程处理一个 Queue）
consumer.registerMessageListener(new MessageListenerOrderly() {
    @Override
    public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ConsumeOrderlyContext context) {
        // 单线程顺序处理
        return ConsumeOrderlyStatus.SUCCESS;
    }
});
```
顺序的代价
```
// ① 一个 Queue 只有一个消费者线程（吞吐下降）
// ② 一个消费者阻塞 → 该 Queue 消息全部等待
// ③ 只保证分区内有序（不同 key 可以并行）

// 设计：
// 分区顺序 = 顺序 + 并行的平衡
```

### 集群模式和广播模式的区别
```
// 集群：一条一人（分工）
// 广播：一条所有人（复制）
```

```
// 集群：Broker

```
#### 怎么保证顺序消息
```
// 生产：同一 key 选同一 Queue（hash）
// 消费：顺序消费（单线程）
```
#### 全局顺序和分区顺序
```
// 全局：1 个 Queue（吞吐低）
// 分区：同一 key 有序（可并行）
```

```
// 重试队列（16 次）→ 死信队列 → 人工处理
```
会重复消费吗
```
// 会！消费进度未提交时挂了 → 重启重新消费
// 解决：业务幂等
```
