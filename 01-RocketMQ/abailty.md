## 可靠性
可靠性总览->刷盘机制->复制机制->组合矩阵->生产端可靠->消费端可靠->面试高频题
### 可靠性总览
消息不丢的三个环节
```
// ① 生产端：发送可靠（确认 + 重试）
// ② Broker：存储可靠（刷盘 + 复制）
// ③ 消费端：消费可靠（确认 + 重试）

// 任何一个环节丢了 → 消息丢失！

Producer ──①发送──→ Broker ──②存储──→ Consumer
             可靠              可靠       ③消费可靠
```
### 刷盘机制
| 刷盘方式     | 说明           | 可靠性    | 性能  |
| -------- | ------------ | ------ | --- |
| **同步刷盘** | 写入磁盘后才返回成功   | 高（不丢）  | 低   |
| **异步刷盘** | 写入内存就返回，异步刷盘 | 中（宕机丢） | 高   |
```
// 配置：
flushDiskType=ASYNC_FLUSH  // 异步刷盘（默认，性能好）
flushDiskType=SYNC_FLUSH   // 同步刷盘（可靠）
```
为什么同步刷盘可靠
```
// 异步刷盘：
// ① 消息写入内存（PageCache）
// ② 返回发送成功
// ③ 后台异步刷到磁盘
// 宕机（没来得及刷）→ 内存数据丢失 → 消息丢！

// 同步刷盘：
// ① 写入内存
// ② 强制刷到磁盘（fsync）
// ③ 刷盘成功才返回
// 宕机 → 已落盘 → 不丢 ✅
```
权衡
```
// 生产建议：
// ① 金融/订单等核心消息 → 同步刷盘（可靠性）
// ② 日志/统计等非核心 → 异步刷盘（性能）
// ③ 一般项目用异步刷盘 + 主从同步复制（也够）
```
### 复制机制
| 复制方式     | 说明        | 可靠性 | 性能  |
| -------- | --------- | --- | --- |
| **同步复制** | 从节点确认后才返回 | 高   | 低   |
| **异步复制** | 主节点写完就返回  | 中   | 高   |
```
// 配置：
brokerRole=ASYNC_MASTER  // 异步复制主
brokerRole=SYNC_MASTER   // 同步复制主
brokerRole=SLAVE         // 从节点
```
为什么需要复制
```
// 主节点宕机 → 数据还在从节点 → 不丢
// 没复制：
// 主节点宕机 → 未复制的消息丢失！

// 同步复制：
// 主写 → 从也写成功 → 才返回 ✅ 双保险
// 从挂了 → 主写失败？→ 主仍写入（降级）
```
### 组合矩阵
| 刷盘 + 复制         | 可靠性  | 性能  | 场景    |
| --------------- | ---- | --- | ----- |
| **异步刷盘 + 异步复制** | 最低   | 最高  | 日志    |
| **同步刷盘 + 异步复制** | 中    | 中   | 一般业务  |
| **异步刷盘 + 同步复制** | 中    | 中   | 一般业务  |
| **同步刷盘 + 同步复制** | 最高 ✅ | 最低  | 金融/订单 |
```
// 面试回答：
// "RocketMQ 的可靠性由刷盘 + 复制两个维度决定：
// 刷盘（异步/同步）解决'单机宕机不丢'，
// 复制（异步/同步）解决'主节点宕机不丢'。
// 生产最可靠：同步刷盘 + 同步复制。
// 一般业务：异步刷盘 + 同步复制（性能可靠平衡）。"
```
### 生产端可靠
发送流程
```
// ① 同步发送：等 Broker 确认
// ② 失败 → 重试（默认 2 次）
// ③ 重试还失败 → 返回失败（应用处理）

// 关键：发送失败必须处理！
// 不能"发了就不管"（单向发送会丢）

// 生产可靠套路：
// ① 同步发送 + 重试
// ② 失败 → 存本地/DB（待补偿）
// ③ 定时重发
```
发送消息不丢的配置
```
// ① 同步发送（确认）
producer.send(msg);

// ② 重试次数
producer.setRetryTimesWhenSendFailed(3);

// ③ 失败补偿（事务消息或本地表）
// 发送失败 → 记录 → 定时重发
```
### 消费端可靠
消费流程
```
// ① 拉取消息
// ② 消费处理
// ③ 返回状态（确认）
//    CONSUME_SUCCESS：成功（提交进度）
//    RECONSUME_LATER：失败（重试）
```
消费不丢的关键
```
// ① 消费成功才确认（先业务后 ack）
// ② 失败返回重试（不要吞异常当成功！）
// ③ 重试 16 次仍失败 → 死信队列
// ④ 死信要监控处理（不能一直堆积）

// 注意：
// ① 先业务再确认（确认了但业务失败 → 丢！）
// ② 重复消费靠幂等（不是靠确认防）
```
消费端消息丢失场景
```
// 场景：先 ack 后业务？
// 消息确认了 → 业务处理中崩溃 → 消息已确认 → 丢失！
// 正确：先处理业务 → 成功 → 再 ack

// 场景：业务异常被吞
// catch 后返回 SUCCESS → 消息当成功 → 丢失！
// 正确：异常返回 RECONSUME_LATER（重试）
```
### 面试高频题
#### 消息丢失有几个环节
```
// 生产（确认+重试）、Broker（刷盘+复制）、消费（确认+重试）
```
#### 同步刷盘和异步刷盘
```
// 同步：写磁盘才返回（可靠慢）
// 异步：写内存返回（快可能丢）
```
#### 同步复制和异步复制
```
// 同步：从节点确认才返回（可靠慢）
// 异步：主写完返回（快可能丢）
```
#### 最可靠的配置
```
// 同步刷盘 + 同步复制
// 一般用异步刷盘 + 同步复制
```
#### 消费端怎么防丢
```
// 先业务后 ack、失败重试、死信监控
```
生产端怎么防丟
```
// 同步发送 + 重试 + 失败补偿
```
