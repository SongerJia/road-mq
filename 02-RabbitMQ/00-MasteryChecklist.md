## 1. 核心概念与消息流转？

**锚点**：官方文档 Getting Started / AMQP 协议

- [ ] **及格**：消息路径——**生产者 → 交换机（Exchange）→ 队列（Queue）→ 消费者**；交换机与队列通过 **Binding** 关联；四种交换机类型（**direct / topic / fanout / headers**）
- [ ] **良好**：及格 + 能解释——交换机**不存储消息**，只负责路由；队列才存储；**Connection vs Channel** 的区别（Connection 是 TCP 长连接，Channel 是连接内的轻量通道，多路复用）
- [ ] **精通**：良好 + 能应对追问——**为什么用 Channel 而不是一个连接一个线程**（减少 TCP 开销，channel 复用）、消息投递失败会怎样（路由不到队列 → 丢弃或 Return 回调）、消费者如何限流（prefetch）

## 2. 交换机与路由规则？

**锚点**：官方文档 Exchanges

- [ ] **及格**：三种常用类型——**direct**（路由键精确匹配）、**topic**（通配符：`*` 匹配一个词，`#` 匹配零或多个）、**fanout**（广播，忽略路由键）
- [ ] **良好**：及格 + 能说出典型场景——direct 做点对点/按 key 分发、topic 做**业务分类订阅**（如 `order.created.*`）、fanout 做广播通知；路由键（routing key）与绑定键（binding key）的匹配过程
- [ ] **精通**：良好 + 能应对追问——**headers 交换机**什么时候用（按消息头匹配，复杂条件）、交换机**没有绑定队列会怎样**（消息被丢弃）、`mandatory` 参数 + `ReturnListener` 的配合、如何实现**备份交换机**（Alternate Exchange）

## 3. 可靠性：确认机制与持久化？

**锚点**：官方文档 Publisher Confirms / Reliability

- [ ] **及格**：三段防护——生产者 **confirm 确认**、消费者**手动 ack**、**持久化三件套**（交换机 / 队列 / 消息都 durable + persistent）
- [ ] **良好**：及格 + 能解释——confirm 的三种模式（**普通 / 批量 / 异步**，异步性能最好）；消费端 `basicAck` / `basicNack`（`requeue` 是否重回队列）；持久化的代价（刷盘，吞吐下降）
- [ ] **精通**：良好 + 能应对追问——**消息丢失的三个环节**（生产 / RabbitMQ 内 / 消费）各自怎么防、**mandatory + Return 回调**处理路由失败的消息、持久化消息的 fsync 时机（可能仍丢少量）、confirm 与事务模式（`txSelect`）的区别（confirm 不阻塞）

## 4. 死信队列（DLX）与 TTL？

**锚点**：官方文档 Dead Letter Exchanges / TTL

- [ ] **及格**：**DLX = 死信交换机**——队列绑定 DLX 后，死信消息被转发到死信队列；**TTL** = 消息过期时间
- [ ] **良好**：及格 + 能说出——消息变为**死信的三种条件**（消费者拒绝且不 requeue / 消息过期 / 队列长度满）；TTL 的两种设置（**队列级**与**消息级**，先到先生效）；**延迟队列 = TTL + DLX** 的经典实现
- [ ] **精通**：良好 + 能应对追问——死信消息的**处理方案**（人工补偿/定时重投/告警）、**为什么 RabbitMQ 不原生支持延迟队列**（官方插件 rabbitmq-delayed-message-exchange 的取舍）、过期消息的清理时机（惰性删除）、TTL 设为 0 的用途（测试/立即过期）

## 5. 高可用：镜像队列？

**锚点**：官方文档 Mirrored Queues / Clustering

- [ ] **及格**：**镜像队列**把队列复制到集群多个节点（一个 master + 多个 slave），master 挂掉 slave 提升；节点类型——**内存节点 / 磁盘节点**
- [ ] **良好**：及格 + 能解释——镜像同步机制（GM 协议，发布确认等待所有镜像同步）、故障转移流程、镜像队列 vs 普通集群的区别（普通集群只有元数据共享，队列数据在单节点）
- [ ] **精通**：良好 + 能应对追问——镜像队列的**性能代价**（每次发布要同步所有镜像，吞吐下降）、**Quorum Queue（仲裁队列）** 新方案（Raft 共识，替代镜像队列，官方推荐）、脑裂/网络分区时的处理、镜像队列与持久化的关系
