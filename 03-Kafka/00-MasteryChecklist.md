## 2. 存储机制：为什么 Kafka 吞吐高？

**锚点**：官方文档 Log / 源码 `LogSegment`

- [ ] **及格**：分区存储为多个 **segment**（`.log` 数据 + `.index` 稀疏索引 + `.timeindex` 时间索引）；**顺序写磁盘**
- [ ] **良好**：及格 + 能解释高吞吐的底层——**顺序写**（磁盘顺序 IO 接近内存速度）+ **OS page cache**（读写走内核页缓存，不做多余缓存）+ **批量**（batch 攒批发送）+ **压缩**（gzip/snappy/lz4/zstd）+ **零拷贝**（sendfile）
- [ ] **精通**：良好 + 能应对追问——**为什么索引是稀疏的**（只索引部分 offset，靠二分 + 顺序扫描补齐）、日志清理策略（**delete 按时间/大小** vs **compact 按 key 保留最新**）、segment 为什么固定大小/时间滚动、**零拷贝具体省了什么**（避免用户态/内核态拷贝与上下文切换）

## 3. 副本机制与 ACK：消息会丢吗？

**锚点**：官方文档 Replication / 设计原理

- [ ] **及格**：每个分区有 leader + follower（follower 只从 leader **拉取**数据）；生产者 **acks** 参数——`0`（不等确认，可能丢）、`1`（leader 写入即确认）、`all`（所有 ISR 确认）
- [ ] **良好**：及格 + 能解释——**ISR**（in-sync replicas，与 leader 保持同步的副本集合）、follower 落后/宕机会被**踢出 ISR**、`min.insync.replicas` 配置；**HW（高水位）/ LEO** 概念（follower 只追到 HW，防止读到未同步数据）
- [ ] **精通**：良好 + 能应对追问——**acks=all 就一定不丢吗**（不——ISR 只剩 leader 时仍会丢，需配 `min.insync.replicas`）、leader 选举（从 ISR 选，ISR 空时可用 `unclean.leader.election` 但会丢数据）、**数据丢失的经典场景**（leader 宕机 + 新 leader 没有旧数据 + 旧 leader 恢复后被截断）、HW 与 LEO 的更新时机

## 4. 消费组与重复消费？

**锚点**：官方文档 Consumer Group / 精确一次语义

- [ ] **及格**：**消费组**内部分区被组内消费者瓜分（一个分区同一时刻只被组内一个消费者消费）；offset 提交（手动/自动）
- [ ] **良好**：及格 + 能解释——分区分配策略（**Range / RoundRobin / Sticky**）、**再平衡（Rebalance）**触发条件（消费者加入/离开/订阅变化）与影响（stop-the-world 式重新分配）、`enable.auto.commit` 的**坑**（处理完提交前崩溃 → 重复消费）

## 5. Kafka vs RocketMQ 怎么选型？

**锚点**：官方文档对比 / 业界实践

- [ ] **及格**：各自的**定位**——Kafka：高吞吐、日志/流式场景王者；RocketMQ：业务消息（事务、延迟、顺序）更顺手；RabbitMQ：轻量、路由灵活、中小规模
- [ ] **良好**：及格 + 能说出关键差异——**吞吐**（Kafka 顺序写 + 零拷贝更高）、**延迟/可靠性语义**（Kafka at-least-once/精确一次、RocketMQ 消息轨迹与重试更完善）、**功能**（RocketMQ 原生延迟/事务消息，Kafka 需自建）、生态（Kafka Streams / Connectors）
- [ ] **精通**：良好 + 能应对追问——**具体场景决策**（日志采集/数据管道选 Kafka；订单/支付等核心业务选 RocketMQ；复杂路由/小体量选 RabbitMQ）、Kafka 强在吞吐为何不适合强一致场景、消息堆积时两家的处理差异、Kafka 的**消费滞后监控**（`kafka-consumer-groups` 命令 / lag）
