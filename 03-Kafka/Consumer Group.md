### 消费模型
两种消费方式

|方式|说明|场景|
|---|---|---|
|**单消费者**|一个消费者消费所有分区|简单|
|**消费者组**|组内分摊分区|✅ 生产常用|
```
Topic（3 分区）：
┌──────────────┐
│ p0 │ p1 │ p2 │
└──────────────┘
  ↓ 消费组 group1（2 个消费者）
消费者 A → p0, p1
消费者 B → p2
（分摊，一条消息只被一个消费者处理）
```
### Consumer Group
```
// 多个消费者组成一个组（groupId）
// 组内共享 Topic 的分区（分摊消费）
// 类似 RocketMQ 集群模式

// 关键：
// ① 一个分区同一时刻只能被组内一个消费者消费
// ② 一条消息只被组内一个消费者处理
// ③ 不同组各自消费（互不影响）

// 场景：订单处理服务 3 个实例 = 一个组
// 分摊处理订单消息（不重复）
```
组 vs 单消费者
```
// 单消费者：所有分区都它消费（吞吐低）
// 消费组：分区分摊（吞吐高、容错好）

// 消费组 = 负载均衡 + 高可用
```
### 分区分配策略
| 策略                 | 说明       | 特点      |
| ------------------ | -------- | ------- |
| **Range（范围）**      | 按分区范围分   | 默认，可能不均 |
| **RoundRobin（轮询）** | 轮流分配     | 均匀      |
| **Sticky（粘性）**     | 尽量保持原有分配 | 减少重分配   |
分配示例
```
// Topic 4 分区（p0-p3），组 2 个消费者（A、B）

// Range：
// A → p0, p1
// B → p2, p3
// （按范围切）

// RoundRobin：
// A → p0, p2
// B → p1, p3
// （轮流）

// 注意：消费者数 > 分区数 → 有消费者空闲
// 分区数 > 消费者数 → 有的消费者分多个
```
### offset管理
offset是什么
```
// 消费者消费到分区的位置（偏移量）
// 记录"下次从哪开始消费"

// 存哪：__consumer_offsets 主题（Kafka 内部）
// 自动提交 / 手动提交
```
两种提交方式
```
// ① 自动提交（默认，enable.auto.commit=true）
//    定时自动提交（auto.commit.interval.ms，默认 5s）
//    风险：提交了但没处理完 → 丢；没提交处理完 → 重复

// ② 手动提交（推荐，可靠）
//    enable.auto.commit=false
//    处理完再提交

// 手动提交：
consumer.commitSync();    // 同步提交（阻塞）
consumer.commitAsync();   // 异步提交（不阻塞）
```
消费位置
```
// ① earliest：从头消费（最早）
// ② latest：从最新开始（默认）
// ③ none：报错（找不到 offset 时）

// 重置 offset（重新消费）：
consumer.seek(partition, 0);  // 从头
```
### Rebalance 再平衡
```
// Rebalance：消费者组成员变化时，重新分配分区
// 触发时机：
// ① 消费者加入/退出
// ② 消费者挂掉
// ③ 分区数量变化
// ④ 订阅变化
```
过程
```
// ① 触发（有成员变化）
// ② 所有消费者暂停消费
// ③ 重新分配分区
// ④ 新分配生效，恢复消费

// 问题：
// ① 暂停期间不消费（服务中断）
// ② 可能重复消费（分配变化）
// ③ 频繁 Rebalance = 频繁中断（性能问题）
```
减少Rebalance影响
```
// ① 设置合理的 session.timeout（会话超时）
// ② 用 Sticky 策略（尽量保持分配）
// ③ 避免消费者频繁启停
// ④ 心跳正常（不误判挂掉）

// 注意：消费中处理慢 → 心跳超时 → 被踢出组 → Rebalance
// 处理慢时：max.poll.interval.ms 调大
```
**Q:** "什么是 Rebalance？有什么影响？" 
**A:** "消费者组成员变化时重新分配分区。影响：① 暂停消费（服务中断）；② 可能重复消费；③ 频繁触发性能下降。减少：合理的 session.timeout、Sticky 策略、避免频繁启停。"
### 重复消费与乱序
为什么重复消费
```
// ① 提交 offset 前崩溃 → 重启重新消费
// ② Rebalance 时分区换人 → 新消费者从头（旧 offset）
// ③ 手动提交失败

// 处理：业务幂等
```
为什么乱序
```
// ① 同一 key 消息进了不同分区 → 不同消费者 → 乱序
// ② 分区分配变化 → 顺序被打乱

// 保证顺序：
// ① 同一 key 进同一分区（key 哈希）
// ② 分区内有序（追加写）
// ③ 一个分区一个消费者（组内）

// 生产端指定 key：
producer.send(new ProducerRecord<>("topic", "order-" + orderId, msg));
// 同一 orderId → 同一分区 → 有序
```
分区内顺序保证
```
// ① 生产：同一 key → 同一分区（哈希）
// ② 存储：分区内追加写（有序）
// ③ 消费：一个分区只被一个消费者（有序消费）

// 只保证"分区内"有序，跨分区无序
// 与 RocketMQ 分区顺序同理
```
