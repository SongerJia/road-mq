## 存储机制
为什么Kafka快->顺序写->日志分段->页缓存->零拷贝->高吞吐全景->面试高频题
### 为什么kafka吞吐高
```
// 四大原因：
// ① 顺序写磁盘（不随机写）
// ② 页缓存（PageCache，不用自己管缓存）
// ③ 零拷贝（减少数据拷贝）
// ④ 批量 + 分区并行

// 看似矛盾：Kafka 用磁盘为什么还快？
// 因为：
// ① 顺序写磁盘 ≈ 内存写（现代磁盘顺序写很快）
// ② 随机写才慢（磁头跳转）
// ③ 利用页缓存（OS 层缓存）

// 顺序写 500MB/s+，随机写只有 20MB/s 左右
```
### 顺序写 Append-Only
消息追加写
```
// 消息写入分区日志 = 尾部追加（append only）
// 不修改、不删除（顺序追加）

// 分区日志：
// [msg0][msg1][msg2][msg3]...  ← 永远在尾部追加

// 好处：
// ① 顺序 IO（磁盘顺序写快）
// ② 不用查找（定位尾部即可）
// ③ 不用随机写（无碎片）
```
对比随机写
```
// MySQL（随机写为主）：
// 更新数据 → 找到位置 → 覆盖写 → 随机 IO

// Kafka（顺序写）：
// 发消息 → 尾部追加 → 顺序 IO

// 这就是 Kafka 不用内存也能高吞吐的原因
```
### 日志分段 LogSegment
为什么分段
```
// 分区日志无限增长 → 不可能一个文件
// 分段：按大小/时间分成多个段（segment）

// partition-0：
// ┌────────┐ ┌────────┐ ┌────────┐
// │ seg-0  │ │ seg-1  │ │ seg-2  │  ← 每段独立文件
// └────────┘ └────────┘ └────────┘
//  1GB        1GB        1GB

// 每个分段包含：
// ① .log：消息数据
// ② .index：偏移量索引（稀疏）
// ③ .timeindex：时间索引
```
分段的好处
```
// ① 便于清理（删旧段 = 删过期数据）
// ② 便于查找（索引定位段）
// ③ 便于备份恢复
// ④ 控制单文件大小（默认 1GB）
```
消息清理策略
```
// ① delete：删除过期段（默认）
//    按时间（retention.ms，默认 7 天）
//    按大小（retention.bytes）
// ② compact：压缩（保留 key 最新值）

// 注意：Kafka 不会立即删除消息
// 默认保留 7 天（可重放、可回溯）
```
### 页缓存 PageCache
```
// Kafka 用 OS 的页缓存（PageCache）
// 不自己管理缓存（不像 MySQL 的 Buffer Pool）

// 写入：
// ① 消息写到 OS 页缓存（内存）
// ② 后台异步刷盘（或刷盘策略）
// ③ 读的时候：优先页缓存命中（内存）

// 好处：
// ① 写快（先写内存）
// ② 读快（命中内存）
// ③ 不用自己实现缓存（省心）
```
和MySQL对比
```
// MySQL：自己管理 Buffer Pool（内存大小自己控制）
// Kafka：用 OS 页缓存（系统自动管理）

// Kafka 的优势：
// ① 缓存可用整个内存（OS 管）
// ② 冷热数据自动处理
// ③ 不用配置（省事）
```
刷盘
```
// ① 默认：消息进页缓存就返回（快，但可能丢）
// ② 可配 acks=all + 刷盘参数（可靠）

// 和 RocketMQ 类似：异步刷盘（快）vs 同步刷盘（稳）
```
### 零拷贝 Zero Copy
传统数据拷贝（4次）
```
// 发送文件给客户端（传统 4 次拷贝 + 4 次切换）：

// ① 磁盘 → 内核缓冲区（read）
// ② 内核 → 应用缓冲区（CPU 拷贝）
// ③ 应用 → Socket 缓冲区（CPU 拷贝）
// ④ Socket → 网卡（write）

// 两次 CPU 拷贝（②③）浪费
// 大量上下文切换（用户态/内核态）
```
Kafka零拷贝（2次）
```
// Kafka 消费时用 sendfile（零拷贝）：
// ① 磁盘 → 内核缓冲区（DMA）
// ② 内核缓冲区 → 网卡（DMA，不经过应用）

// 效果：
// ① 去掉 2 次 CPU 拷贝
// ② 减少上下文切换
// ③ 大幅提升吞吐

// Java 实现：FileChannel.transferTo()
// 底层是 sendfile 系统调用
```
### 批量+压缩
批量发送
```
// Producer 批量收集消息再发送（batch）
// ① 减少网络往返
// ② 一次请求多条消息
// ③ 吞吐大幅提升

// 参数：
// batch.size（默认 16KB）
// linger.ms（等待积攒时间，默认 0）
```
压缩
```
// 批量消息可压缩（gzip/snappy/lz4/zstd）
// ① 减少网络传输
// ② 减少磁盘占用
// ③ CPU 换带宽

// 注意：压缩在"批量"下收益最大
```
### 高吞吐全景
```
Producer 高吞吐：
 ① 批量发送
 ② 压缩
 ③ 分区并行（多个分区同时写）
    ↓
Broker 高吞吐：
 ① 顺序写（append-only）
 ② 页缓存（先内存）
 ③ 日志分段（管理方便）
    ↓
Consumer 高吞吐：
 ① 批量拉取
 ② 零拷贝（sendfile）
 ③ 分区并行消费
```
**Q:** "Kafka 为什么吞吐这么高？" 
**A:** "① 顺序写磁盘（append-only，顺序 IO 快）；② 用 OS 页缓存（先写内存）；③ 零拷贝（sendfile，减少拷贝）；④ 批量发送 + 压缩；⑤ 分区并行。核心是'顺序写 + 零拷贝'把磁盘用到了极致。"
### 面试高频题
#### 题目1：kafka存储用什么
```
// 分区日志 + 顺序追加写
// 分段管理（LogSegment）
```
#### 题目2：为什么顺序写快
```
// 顺序 IO 无磁头跳转
// 顺序写 ≈ 内存速度级别
```
#### 题目3：页缓存是什么
```
// OS 层缓存，Kafka 直接用
// 写先入内存，读命中内存
```
#### 题目4：零拷贝怎么做到
```
// sendfile：磁盘 → 内核 → 网卡
// 跳过应用层（2 次拷贝 vs 4 次）
```
#### 题目5：消息保留多久
```
// 默认 7 天（retention.ms）
// 可回溯消费
```
#### 题目6：消息会立即删除吗
```
// 不会！分段清理（delete/compact）
// 过保留期才清
```
